## 0. 先对齐口径：2D 与 3D 不是同一任务

- 2D 的 77.4%：**GT 最佳 mask 在查询视角所有 mask 中被文本排到第 1** 的比例（found 96/124）。
  这是“给定正确 mask，特征能不能被文本认出来”。
- 3D 的命中率：用某种聚合特征在**候选池**里选中 GT 最佳候选的比例（found 124 条）。
  这是“聚合后的特征还能不能认出物体”。

**关键结论（修正后）**：
1. **3D 聚合确实比 2D 差，但不是均匀地差**：去掉 teatime，Phase A id_top3 为 60/70=**85.7%**、
   Phase B 为 54/70=**77.1%**，与 2D 的 77.4% 接近；teatime 单独把总命中拖到 0.653/0.524。
   teatime 占 found 的 54/124（44%），所以它的塌陷主导了总体。
2. **一致性聚合在所有场景都崩**：Phase A agree 0.083–0.381、Phase B agree 0.000–0.524，
   总命中仅 13.7%/15.3%。这不是“3D 聚合”的问题，是**查询无关权重**的问题。
3. 因此问题有两层：**(a) 3D 聚合在 teatime 这类场景会被稀释/混合拖垮；(b) 一致性在任何场景都不可用于评分。**

## 1. 为什么一致性聚合会把 found 打崩

一致性聚合的权重/保留规则只依赖“视角之间像不像”，**完全不知道当前 query 是什么**。
在区域/掩码混合特征上，这会导致四个连锁效应：

1. **它优化的是“共享成分”，不是“物体成分”。**
   区域特征 = 物体 + 背景/场景共享语义。跨视角最一致的部分往往是共享语义
   （墙、桌面、房间光照），而不是物体。q_i 的分布很紧（只剔除 4.8%），
   被剔掉的尾部恰恰是“和共识不一样”的视角——也就是物体最显著、最独特的视角。
2. **剔除后，聚合特征向场景原型靠拢。**
   保留下来的是“最像大家”的视角，均值更接近 scene prototype；
   文本对齐（object-specific）反而下降，通用/背景候选的分数上升。
3. **found 查询本来已经排对，任何查询无关的扰动都在破坏它。**
   found 的 released 选择是正确的；一致性特征在 **84.7–86.3%** 的 found 查询上选中了另一个候选
   （命中率仅 13.7–15.3%）。这不是“微调”，是把已经对的排序翻掉。
4. **它偏爱大区域/多视角候选。**
   视角越多、区域越大，越容易形成“共识”；小物体、少见视角的候选被系统性压制。
   这与 found 查询里小物体的失败方向一致。

**因果性**：上表是同一特征、同一池、同一文本，只换算子。Phase A id_top3 65.3% → agree 13.7%，
Phase B id_top3 52.4% → agree 15.3%；落差只能由“一致性算子”本身解释，不是特征差、不是池差。

## 2. 更深的原则：开放词汇的身份是“查询相对的”

同一个区域，query 是 “table” 还是 “plate”，哪些视角是“有效证据”是不同的。
- **查询条件化**（文本 top-k / 文本加权）：知道当前要找什么，保留对该 query 有证据的视角。
- **查询无关**（一致性、中心化、scene prototype、白化）：不知道 query，只能优化“大家共同的部分”，
  于是收敛到共享语义。

这解释了此前所有“中性/失败”的结果：
- C1（减 scene mean）对检索排序是常数平移 → 不改变结果；
- ROFA（一致性剔除）中性/空操作；
- 白化破坏文本对齐；
- 一致性选 2D mask 反而更差（xview 0.4003/0.3038，support-only 0.0251）；
- 一致性聚合 found 13.7–15.3%。

**一句话：一致性是“关联先验”，不是“评分权重”。**
它应该用来分组/建实例（association），不应该用来聚合特征做文本打分（scoring）。

## 3. 可检验的预测

如果上述机制成立：

1. **按文本加权的一致性**（保留文本证据强且相互一致的视角）应当优于纯一致性，
   并接近/超过 id_top3。
2. 一致性造成的 found 下降，应当在“物体占区域比例小、视角数多、背景共享强”的查询上更大。
3. 用一致性只做**分组**、聚合仍用文本权重，应当不伤 found。
4. 同一个区域换 query，文本 top-k 选中的视角集合应显著变化（查询相对性）。

## 4. 应该怎么做（方法含义）

- **评分路径**：永远用查询条件化的权重（文本 top-k 或 softmax 文本权重）聚合原始 CLIP 特征。
- **关联路径**：用几何/一致性把视角/mask 分组成实例，但分组后的评分仍回到文本。
- **不要**把一致性分数、scene prototype、白化后的特征直接送进文本打分。

这条原则同时解释了“2D 好 3D 差”的错觉：**查询无关**的 3D 聚合（一致性/中心化/白化）在任何场景都坏；
**查询条件化**的聚合在 3/4 场景接近 2D（fig/ramen/waldo 的 id_top3 约 0.77–0.89），
但 teatime 会被稀释/混合拖垮（0.20–0.39）。所以剩余差距既在聚合（teatime 的实例稀释），
也在候选池/实例形成，而不是“3D 聚合天然不行”。
