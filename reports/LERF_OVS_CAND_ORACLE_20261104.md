# LERF-OVS：三维候选可恢复性（Oracle 实验，2026-11-04）

性质：**只测候选可恢复性**，不实现 Grounded-SAM 融合、不加门控、不训任何东西。
所有数字在 fj01 上实测；原始 `nag_data.py`、ROFA、NAG 模型、评测器与既有结果均未改动。

---

## 0. 结论

**是。ReLaGS 的三维层级里已经存在明显更正确的候选区域，读端的损失主要发生在"选"而不是"造"。**

在官方口径（先图像平均、再场景平均、四场景 macro）下，基线逐位复现 **0.6401**，
而把候选池从"top-5 根 + gap 截断"放宽到"层级里已存在的其他节点"后：

| 候选池 | macro mIoU | Δ vs 基线 |
|---|---:|---:|
| C0 原始预测 | **0.6401** | — |
| + top-5 根节点（Root Oracle） | **0.7374** | **+9.73** |
| + 原始层级细化节点（Hierarchy Oracle，gap 过滤前） | 0.7384 | +9.83 |
| + 受约束节点组合（Combination Oracle） | 0.7515 | +11.14 |
| 细粒度单节点（level 1/2，超出原协议） | 0.7788 | +13.88 |
| 根 top-10 + 细粒度单节点（Deep，超出原协议） | 0.8061 | +16.60 |
| 全部候选池合并（Grand） | **0.8191** | **+17.90** |

三个可直接落地的读法：

1. **根节点选择是主因**：只把"选哪个根"放开到 top-5 内，就 +9.7pp。
2. **原始层级细化几乎没贡献**（Hierarchy − Root = +0.10pp）：因为 `_analyze_leaf_candidates`
   只在 top-5 根内部、且只下降一层（level 3→2），它救不了"根选错"。
3. **细粒度节点才是最大的未用池**（+13.9pp）：level 1/2 的节点有 CLIP 特征、可无标签排序，
   但发布的搜索从不全局考虑它们。

一个必须单独记录的发现：**208 条查询里有 18 条（8.7%）原始预测 `pred_px = 0`**。
这些查询的 `n_candidates` 是 1–6（不是 0），真实原因是**被选中的三维节点在该查询视角下不可见**
（可见高斯占比中位数 0%），而不是 gap 规则截断成空集。其中 13 条在现有候选池里能恢复到 IoU > 0.5
（ramen 9、figurines 2、waldo 2）。详见 §3。

## 3. 空预测：不是空集，是"选中节点在该视角不可见"

18 条 `pred_px = 0` 的查询，`n_candidates` 都是 1–6，**没有一条是 gap 返回空集**。
用 `render_point` 的逐高斯权重检查它们被选中的节点：

| | 数量 | 选中高斯的可见占比 | 池内可恢复到 >0.5 |
|---|---:|---:|---:|
| `pred_px = 0` 查询 | 18 | 中位 **0.0%**，最大 7.2% | 13 |
| `pred_px > 0` 查询（每场景抽样 8 条） | 32 | 中位 **83.7%** | — |

即：**搜索是视角无关的，它会选中一个语义分数高、但在查询相机里被遮挡或在视野外的三维节点**，
渲染出来自然是空图。这是视角一致性问题，不是候选生成问题。

最干净的例子（ramen，`sake cup`，frame_00006）：

| 项 | 值 |
|---|---|
| 选中根节点 | l3/44（sim 0.561，5495 高斯，可见 0 个） |
| top-5 内另一根 l3/32 下真正对应杯子的子节点 | **l2/45（sim 0.507，IoU 0.964，可见）** |
| 为什么没被考虑 | `_analyze_leaf_candidates` 要求子节点 `leaf_sim > root_sim` 才下钻；0.507 < 0.509（其父根 l3/32），子节点被丢弃，整根保留 |
| 父根是否在 top-5 | 是（l3/32 在 size 过滤后正好第 5）——不是 top-5 截断的问题 |

所以失效是两层叠加的：**跨层级比较原始余弦分数（几乎打平）→ 规则偏向更粗的节点 → 更粗的节点恰好在该视角不可见**。
这解释了为什么 Hierarchy Oracle 几乎等于 Root Oracle（+0.10pp）：发布的细化规则丢掉的正是这些子节点。

按可见性拆分的增益：

| | 数量 | Root 平均增益 | 细粒度平均增益 | Grand 平均增益 |
|---|---:|---:|---:|---:|
| `pred_px = 0` | 18 | +0.370 | +0.548 | **+0.619** |
| `pred_px > 0` | 190 | +0.086 | +0.119 | +0.155 |
| 全部 | 208 | +0.111 | +0.156 | +0.195 |

即使**完全剔除**这 18 条，剩余 190 条的候选池仍有 +8.6pp（root）/ **+11.9pp（细粒度）** /
+15.5pp（grand）的平均增益。所以结论不是"只修这 18 条"就能解释。

## 5. 以 GSAM 为失败探针的 35 条（不是两条语义线的对比）

**先明确：Grounded-SAM 与 ReLaGS/CLIP 不是同一层的两个可替换流程。**

| | ReLaGS / CLIP 语义场 | Grounded-SAM 重观测 |
|---|---|---|
| 支持集 | 场景级、跨视角聚合后的 superpoint 层级 | 单帧 2D 检测框 + SAM 掩膜 |
| 持久性 | 烘进场景表示，查询时复用 | 每个查询、每个视角现算 |
| 粒度 | 固定 4 层 NAG 节点 | 任意 2D 区域，帧间无对应 |
| 分数 | 每个簇/节点的语义分 | 只有检测置信度，没有簇级分数 |

所以两者**不可互换、也不可做语义层晚期融合**：要"替换"就得把 GSAM 逐视角 lift 再聚合，
那正是历史上失败的一步；要"融合"就得两边是同支持、同粒度的场，而 GSAM 不是场。

本节只用 GSAM 做一件事：**挑出 C0 灾难性失败的查询**（`gate3d.csv` 里
`gsam3d > clip3d + 0.05` 的 35 条，145 条配对子集内）。GSAM 的 IoU 只是"这些查询确实很难"的
外部旁证，不作为比较对象，也不进入候选构造。35 条是按 GSAM 自身优势选出的，**任何比例都不能
当作无偏估计**——无偏结论看下面全 208 条。

| 指标（仅作失败探针） | 值 |
|---|---:|
| C0 IoU 中位 / 均值 | 0.144 / 0.329 |
| GSAM 单视角输出 IoU 中位 / 均值（旁证） | 0.912 / 0.823 |
| 现有候选 Grand Oracle 中位 / 均值 | 0.870 / 0.793 |
| Grand 相对 C0 提升 >0.05 的条数 | **26/35** |
| Grand 提升 >0.10 的条数 | 24/35 |
| 无任何 ≥0.05 提升（池内覆盖失败） | **9/35** |

逐场景分布：ramen 18、figurines 9、teatime 5、waldo 3。

**读法**：这 35 条是 C0 的灾难性失败（中位 0.144）；其中 **26 条的 3D 候选池里本来就有
提升 >0.05 的候选**，9 条没有。也就是说，失败查询里约四分之三不需要任何二维重观测，
只要在 ReLaGS 自己的层级里换一个候选就能改善。

全 208 条同口径（无选择偏差）：Grand 提升 >0.05 的 75/208、>0.10 的 66/208。
35 条里 26 条（74%）高于全集的 36%，只说明 GSAM 挑出的确实是更容易救的失败查询，
**不能反推"GSAM 的语义更好"或"两者可替换"**。

## 6. 审计：这些数字可信吗

在四个场景上做了三组对照（`analysis/lerf_candoracle_audit.py`，
随机池 seed 20261105，逐查询均值）：

| 场景 | C0 | Deep 池（真 GT） | 同规模随机单节点池 | 置换 GT | CLIP 全局 argmax |
|---|---:|---:|---:|---:|---:|
| figurines | 0.6278 | **0.7763** | 0.6279 | 0.1952 | 0.4068 |
| ramen | 0.5046 | **0.8170** | 0.5063 | 0.1028 | 0.2964 |
| teatime | 0.8022 | **0.8803** | 0.8022 | 0.1581 | 0.6897 |
| waldo_kitchen | 0.6137 | **0.7416** | 0.6137 | 0.0113 | 0.3728 |

三条结论：

1. **没有 GT 泄漏**：候选是用 sims / labels 构造的，GT 只在打分时进入；把 GT 换成下一条查询的
   遮罩后，oracle 从 0.74–0.88 塌到 0.011–0.195（中位 ~0）。若构造环节用过 GT，这个数不会塌。
2. **增益不是"候选变多"**：同规模随机节点池在三个场景上**恰好等于 C0**（ramen 只多 +0.17pp），
   说明增益来自 CLIP 把这些正确节点排进了 top-10，而不是 30 选 1 的统计效应。
3. **但也不能直接拿 argmax 当方法**：跨层级原始余弦不可比，全局 argmax（0.30–0.69）
   在所有场景都低于 C0（0.50–0.80）。**候选存在 ≠ 能无标签选中**，这正是下一轮重排器要解决的问题。

外部锚点（注意是 C1 on，只能比量级，不能逐位比）：仓库里 10-30 的 `lerf_oracle.py` 给出
single_best macro 0.7094、greedy20 0.7791（逐查询均值，C1 on）；本轮逐查询均值为
Hierarchy 0.7414、Deep 0.8038（C1 off，C0=0.6371 vs 对方 0.6396）。排序一致、量级相近；
差 2–3pp，但 C1 on/off 会改变候选池本身，不能逐位归因。

## 7. 这对下一步意味着什么

**支持"在 ReLaGS 自己的三维候选池上重排"，不支持"重构三维候选"。**
也**不支持**把 Grounded-SAM 的二维证据直接拿来重排三维候选：两者支持集不同，
二维证据要进入三维就必须 lift + 跨视角聚合，那正是历史上失败的一步（见 §5）。
二维输出最多只能做逐视角的失败触发/诊断，不能当语义场。重排信号应来自三维侧：

1. 首要修复是**视角一致性**：选中节点必须在查询相机里可见（18 条空预测，13 条池内可恢复）。
   这是最便宜、最可解释的一步，而且完全是三维侧的。
2. 其次修复**跨层级比较**：不要用 `leaf_sim > root_sim` 决定是否下钻；近平分时保留父子两者，
   让后续选择器决定（sake cup 案例：子节点 0.507 vs 父根 0.509，直接丢掉了一个 IoU 0.964 的节点）。
3. 首选候选池：root top-10 ∪ level 1/2 top-10（Deep Oracle 0.8061），
   它同时覆盖"根选错"和"粒度太粗"两类失败。
4. 组合（多实例）只值 +1.3pp，优先级低于"选对单个节点"。
5. 重排信号必须训练-free（与项目既有约束一致）；本轮的 oracle 只给上界，
   不能当作方法结果。

**Oracle 不等于方法。** 上表所有 "+pp" 都来自 `max over candidates`。
本轮只回答"池里有没有"，不回答"能不能无标签选中"；§6 的 argmax 对照说明后者并不平凡。
